## Definition

Violations of the dependency rules approved in `my-specs/general-guidelines/dependency-rules.md`, per rule: each failed architecture test is a violated rule, and its message lists the types and dependencies that break it.

## Execution Context

- Working directory: repository root
- Restore or bootstrap command: `dotnet restore {{solution}}`
- Prerequisite commands: None; the measurement command builds the solution in Release before running the tests
- Version source: the `TngTech.ArchUnitNET` and test framework integration package references in the architecture test project
- Generated results root: `my-specs/measurement/architecture/` (ignored through a `.gitignore` the script writes into it, and recreated on every run)

## Measurement

- Test runner: VSTest through `dotnet test`
- Tool: ArchUnitNET, in the architecture test project's tests marked with `[Trait("Category", "Architecture")]`
- Version: `TngTech.ArchUnitNET` `0.13.4` and the matching integration (`TngTech.ArchUnitNET.xUnit`, `TngTech.ArchUnitNET.xUnitV3`, `TngTech.ArchUnitNET.NUnit`, or `TngTech.ArchUnitNET.MSTestV2`) `0.13.4`, pinned in the architecture test project
- Installation or restore: follow `my-specs/measurement/README.md`, then `dotnet restore {{solution}}`
- Measurement command: `pwsh -NoProfile -File my-specs/measurement/run-architecture-tests.ps1` or `bash my-specs/measurement/run-architecture-tests.sh`, which run `dotnet test {{solution}} --configuration Release --filter "Category=Architecture" --logger "trx;LogFilePrefix=architecture" --results-directory my-specs/measurement/architecture`
- Output format: one TRX per test project, with the `outcome` and failure message of each test, whose name starts with its rule ID
- Result path: `my-specs/measurement/architecture/architecture_*.trx`
- Scope: the rules approved in `my-specs/general-guidelines/dependency-rules.md`, applied to the production assemblies the architecture tests load
- Exclusions: only the one-off exceptions approved in the dependency rules guideline
- Changed-code isolation: run only the rules whose source namespaces the spec changes, repeating `-Rules <ID>` (PowerShell, which also accepts `-Rules DEP-01,DEP-02`) or `--rule <ID>` (Bash)
- Reported values: number of rules run, passed, and violated; and, for each violated rule, its ID and the types and dependencies its failure message names

## Gates

| Reported value | Threshold | Applies to | Enforcement |
| --- | --- | --- | --- |
| Violated dependency rules | `= 0` | Both | Blocking |

Each rule is an architecture decision the team approved, so violating it blocks the inspection, like an exceeded performance budget. A rule without a matching test is `Insufficient evidence`. The architecture tests also run in the `dotnet test` of `my-specs/general-guidelines/build-and-test-commands.md`, so a violation already fails the tests; this metric adds per-rule traceability.

## Related Contract Documents

## Decisions and Tradeoffs

- Express the rules as ArchUnitNET tests: they run with the other tests, on any operating system, without an analysis server.
- Keep the rules in an approved guideline: AI still gets module boundaries wrong, so the team decides the architecture and the tool only checks it.
- Record the rule ID in the test name: TRX does not keep traits, and the name is what ties each result to its rule.
- Use a `Blocking` gate: unlike complexity and coupling, each rule is an explicit, approved boundary rather than an improvement signal.
