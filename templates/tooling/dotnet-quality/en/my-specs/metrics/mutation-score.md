## Definition

Share of production-code mutants the tests detect. Stryker.NET changes the code (operators, conditions, return values, blocks) and runs the tests against each change: a surviving mutant shows behavior no test verifies, even when the line is covered. Score = (killed + timed-out mutants) ÷ (valid mutants, including uncovered ones), per file and in total.

## Measurement

- Tool: Stryker.NET (`dotnet-stryker`), configured by `my-specs/measurement/stryker-config.json`
- Version: `dotnet-stryker` `5.0.0`, pinned in the local tool manifest
- Installation or restore: follow `my-specs/measurement/README.md`, then `dotnet restore {{solution}}` and `dotnet tool restore`
- Measurement command: `pwsh -NoProfile -File my-specs/measurement/run-mutation.ps1` or `bash my-specs/measurement/run-mutation.sh`, which run `dotnet stryker --solution {{solution}} --config-file my-specs/measurement/stryker-config.json --output my-specs/measurement/mutation`
- Output format: Stryker JSON report (mutation-testing-elements schema: `files.<file>.mutants[]` with `status`, `mutatorName`, and `location`) and HTML report
- Result path: `my-specs/measurement/mutation/reports/mutation-report.json`; `my-specs/measurement/mutation/reports/mutation-report.html`
- Scope: every production project in `{{solution}}` exercised by the solution's test projects
- Exclusions: `**/bin/**`, `**/obj/**`, `**/Migrations/**`, `**/*.g.cs`, `**/*.Designer.cs`, `**/*.generated.cs`, `**/AssemblyInfo.cs` (see `mutate` in `my-specs/measurement/stryker-config.json`); mutants with status `CompileError` or `Ignored` do not count toward the score
- Changed-code isolation: mutate only the production files listed in `my-specs/specs/<spec-name>/file-tree.md`, repeating `-Files <path>` (PowerShell, which also accepts `-Files a.cs,b.cs`) or `--file <path>` (Bash) with repository-relative paths; without an approved tree, use `-Since <ref>` or `--since <ref>` with the change's base commit
- Reported values: mutation score with killed, survived, timed-out, and uncovered mutants over the valid total; the score per changed file; and every surviving mutant in the changed files (file, line, and mutator)

## Gates

| Reported value | Threshold | Applies to | Enforcement |
| --- | --- | --- | --- |
| Mutation score of the changed files | `≥ 60%` | Changed code | Attention |

This target matches Stryker's default `low` threshold pinned in `stryker-config.json`, below which its report rates the score as poor. The project-wide score is reported without a gate because mutating the whole solution on every inspection would be too slow.

Every surviving mutant in a changed file is a candidate for a new test or a stronger assertion. An equivalent survivor, whose change alters no observable behavior, is recorded with that justification instead of prompting an artificial test.

## Decisions and Tradeoffs

- Use mutation instead of a coverage gate: a test that runs code without checking its result raises coverage but lets mutants survive.
- Isolate by the spec's file tree: the changed-code score fits the time of an inspection, while the project-wide score is left to quality reports.
- Pin Stryker as a repository-local tool: developers and CI use the same version without a global installation.
- Use an `Attention` gate: a surviving mutant signals a weak test rather than a blocked inspection until the team explicitly adopts a `Blocking` gate.
