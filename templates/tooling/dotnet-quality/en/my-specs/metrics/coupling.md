## Definition

Class coupling: the number of distinct types each developer-controlled type and member uses (parameters, locals, return values, calls, inheritance, and attributes), computed by the .NET analyzer rule CA1506, which also reports how many namespaces those types come from.

## Execution Context

- Working directory: repository root
- Restore or bootstrap command: `dotnet restore {{solution}}`
- Prerequisite commands: None; the measurement command rebuilds the solution in Release with the analyzers
- Version source: the .NET SDK that builds the solution, which ships the analyzers and rule CA1506
- Generated results root: `my-specs/measurement/coupling/` (ignored through a `.gitignore` the script writes into it, and recreated on every run)

## Measurement

- Tool: .NET code quality analyzer rule CA1506, enabled only for this build by `my-specs/measurement/coupling.targets`, `my-specs/measurement/coupling.globalconfig`, and `my-specs/measurement/CodeMetricsConfig.txt`, without changing the projects
- Version: that of the .NET SDK used for the build
- Installation or restore: follow `my-specs/measurement/README.md`, then `dotnet restore {{solution}}`
- Measurement command: `pwsh -NoProfile -File my-specs/measurement/run-coupling.ps1` or `bash my-specs/measurement/run-coupling.sh`, which run `dotnet build {{solution}} --configuration Release --no-restore --no-incremental -p:CustomAfterMicrosoftCommonTargets=<absolute path of coupling.targets> -p:CouplingResultsDirectory=<absolute path of my-specs/measurement/coupling>`
- Output format: one SARIF 2.1 log per production project; each result whose `ruleId` is `CA1506` carries the file and line of the type or member, and its message, in the SDK's language, names the member, the number of types, and the number of namespaces, in that order
- Result path: `my-specs/measurement/coupling/*.sarif`
- Scope: every project in `{{solution}}` that is neither a test project (`IsTestProject`) nor ends in `.Benchmarks`
- Exclusions: generated code (`*.g.cs`, `*.Designer.cs`, `*.generated.cs`, or files with an `<auto-generated>` header), which the analyzers skip by default; results of other rules in the SARIF logs are not part of this metric
- Changed-code isolation: filter the CA1506 results by the production paths listed in `my-specs/specs/<spec-name>/file-tree.md`
- Reported values: number of types above 95 and members above 40 coupled types and, for each one, the type or member, its type and namespace counts, the file, and the line; the rule only reports what exceeds its threshold, so the highest value below it is unknown

## Gates

| Reported value | Threshold | Applies to | Enforcement |
| --- | --- | --- | --- |
| Types with coupling above 95 | `= 0` | Both | Attention |
| Members with coupling above 40 | `= 0` | Both | Attention |

These targets match the CA1506 defaults, pinned in `CodeMetricsConfig.txt` (`CA1506(Type): 95` and `CA1506: 40`); change them there and here together. A type or member above the threshold depends on too many things to change safely, and the expected improvement is to separate responsibilities or depend on the domain's own abstractions. Coupling does not improve merely by hiding dependencies behind facade types with no responsibility of their own.

## Decisions and Tradeoffs

- Use the SDK rule CA1506 instead of the `Microsoft.CodeAnalysis.Metrics` package: the package runs a .NET Framework `Metrics.exe` that only works on Windows, while the analyzers are part of every .NET build.
- Enable the rule through measurement-folder files imported only into this build: regular builds and the repository's `.editorconfig` files stay unchanged.
- Rebuild without incremental build: an up-to-date project would not run the analyzers again or write its log.
- Use `Attention` gates: elevated coupling is an improvement signal rather than a blocked inspection until the team explicitly adopts `Blocking` gates.
