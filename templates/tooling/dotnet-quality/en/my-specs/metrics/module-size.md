## Definition

Executable lines (lines with statements in the Release build, excluding signatures, braces, comments, and blank lines) of each developer-controlled method and class. A class adds up its partial files and the classes the compiler generates for it, such as lambdas and async state machines.

## Measurement

- Tool: Coverlet (`coverlet.collector`), whose Cobertura XML lists each method's executable lines, merged by ReportGenerator, which folds compiler-generated classes into their source class
- Version: `coverlet.collector` `6.0.4`; ReportGenerator `5.5.10`
- Installation or restore: follow `my-specs/measurement/README.md`, then `dotnet restore {{solution}}` and `dotnet tool restore`
- Measurement command: `pwsh -NoProfile -File my-specs/measurement/run-coverage-report.ps1 -NoOpen` or `bash my-specs/measurement/run-coverage-report.sh --no-open`
- Output format: per method, the number of `<line>` elements of each `<method>` in the merged Cobertura XML; per class, the `coverablelines` field of `coverage.assemblies[].classesinassembly[]` in the JSON summary
- Result path: `my-specs/measurement/coverage/report/Cobertura.xml`; `my-specs/measurement/coverage/report/Summary.json`
- Scope: every non-test assembly instrumented by at least one test project in `{{solution}}`
- Exclusions: same as `my-specs/metrics/cyclomatic-complexity.md`
- Changed-code isolation: same as `my-specs/metrics/cyclomatic-complexity.md`
- Reported values: highest executable line count among methods (with the member) and among classes (with the class), and the number of methods above 30 and classes above 300

## Gates

| Reported value | Threshold | Applies to | Enforcement |
| --- | --- | --- | --- |
| Highest executable line count of a method | `≤ 30` | Both | Attention |
| Methods above 30 executable lines | `= 0` | Both | Attention |
| Highest executable line count of a class | `≤ 300` | Both | Attention |
| Classes above 300 executable lines | `= 0` | Both | Attention |

Unlike complexity and the CRAP score, no pinned tool defines a default size boundary: 30 and 300 are an initial proposal to calibrate with the project's first quality report before approval. Read this gate together with the complexity and CRAP gates:

- a long, linear method with low complexity and good coverage is tolerated when its sequence is a single cohesive step, such as an extensive mapping;
- a class above the threshold usually accumulates responsibilities, and the expected improvement is to separate them by behavior;
- size does not improve merely because code was split into arbitrary methods or classes; extracted parts must have cohesive responsibilities.

## Decisions and Tradeoffs

- Measure from the coverage run's Cobertura instead of a code metrics tool: the `Microsoft.CodeAnalysis.Metrics` package runs a .NET Framework `Metrics.exe` that only works on Windows, while Cobertura is already produced on any operating system with no new dependency.
- Count executable lines instead of file lines: comments, blank lines, and formatting do not change the value.
- Accept the scope instrumented by the tests: assemblies without any test stay out of this metric, as they already do for complexity and coverage.
- Use `Attention` gates: a large size is an improvement signal rather than a blocked inspection until the team explicitly adopts `Blocking` gates.
