# .NET quality measurement

This folder was generated by `myspec install --tooling dotnet-quality`. Each script measures a group of metrics under `my-specs/metrics/`:

| Script | Metrics | Tool |
| --- | --- | --- |
| `run-coverage-report` | line and branch coverage, cyclomatic complexity, CRAP score, and module size | Coverlet and ReportGenerator, in a single test run |
| `run-coupling` | type and member coupling | rule CA1506 of the .NET SDK analyzers |
| `run-architecture-tests` | conformance to the dependency rules approved in `my-specs/general-guidelines/dependency-rules.md` | ArchUnitNET |
| `run-mutation` | mutation score | Stryker.NET |
| `run-benchmarks` | allocated bytes and mean time per operation of the critical paths approved in `my-specs/general-guidelines/performance-critical-paths.md` | BenchmarkDotNet |

This folder lives in the workspace, next to `my-specs/metrics/`: the metrics define what to measure and the gates, and this folder holds how to measure it. The scripts find the repository root from their own folder, so they can be run from any directory.

The `myspec` CLI **does not install dependencies**. Follow the steps below before the first run.

## Prerequisites

- A .NET SDK compatible with the project's solution;
- PowerShell 7+ to use the `.ps1` scripts, or Bash for the `.sh` ones (on Windows, Git Bash or WSL);
- access to the NuGet feeds on the first run, to restore packages and local tools;
- Docker running only if the tests use Testcontainers or other container-based infrastructure;
- a single `.sln` or `.slnx` solution at the repository root, or a solution passed explicitly to the script.

## Installing the dependencies

### 1. Test packages

Add the packages to **every test project** the solution runs, replacing the example path with your test project's `.csproj`:

```bash
dotnet add <TestProject>/<TestProject>.csproj package Microsoft.NET.Test.Sdk --version 17.14.1
```

```bash
dotnet add <TestProject>/<TestProject>.csproj package coverlet.collector --version 6.0.4
```

These are the versions recorded in the metric files under `my-specs/metrics/`. If the project already uses other versions, confirm compatibility with the SDK and test framework and update those files before approving them.

### 2. Local tools

ReportGenerator and Stryker.NET are **repository-local** tools, so every developer and CI use the same version. If the repository has no tool manifest yet, create one at the root:

```bash
dotnet new tool-manifest
```

Install the tools into the manifest (`dotnet-tools.json` at the root with the .NET 10+ SDK, `.config/dotnet-tools.json` with earlier SDKs):

```bash
dotnet tool install dotnet-reportgenerator-globaltool --version 5.5.10
```

```bash
dotnet tool install dotnet-stryker --version 5.0.0
```

Coupling needs no installation: rule CA1506 ships with the .NET SDK analyzers and is enabled only in the `run-coupling` build, by this folder's `coupling.targets`, `coupling.globalconfig`, and `CodeMetricsConfig.txt`.

### 3. Architecture test project

The dependency rules are checked by ArchUnitNET tests in a project whose name ends in `.ArchitectureTests`. Create it with the repository's test framework (the example uses xUnit), add it to the solution, and reference the production projects whose dependencies the rules constrain:

```bash
dotnet new xunit -n <Product>.ArchitectureTests -o tests/<Product>.ArchitectureTests
```

```bash
dotnet sln {{solution}} add tests/<Product>.ArchitectureTests/<Product>.ArchitectureTests.csproj
```

```bash
dotnet add tests/<Product>.ArchitectureTests/<Product>.ArchitectureTests.csproj package TngTech.ArchUnitNET.xUnit --version 0.13.4
```

```bash
dotnet add tests/<Product>.ArchitectureTests/<Product>.ArchitectureTests.csproj reference <ProductionProject>/<ProductionProject>.csproj
```

With xUnit v3, NUnit, or MSTest, use `TngTech.ArchUnitNET.xUnitV3`, `TngTech.ArchUnitNET.NUnit`, or `TngTech.ArchUnitNET.MSTestV2` at the same version. The script filters tests by `Category=Architecture` and `Rule=<ID>`; with NUnit or MSTest, confirm the adapter accepts those names in `--filter` and adjust the script if needed.

Each rule in the guideline is one test with the `Architecture` category, the `Rule` trait, and a name that starts with the rule ID, because the TRX report records the test name but not its traits:

```csharp
using ArchUnitNET.Domain;
using ArchUnitNET.Loader;
using ArchUnitNET.xUnit;
using static ArchUnitNET.Fluent.ArchRuleDefinition;
using static ArchUnitNET.Fluent.Slices.SliceRuleDefinition;

public class DependencyRules
{
    private static readonly Architecture Architecture = new ArchLoader()
        .LoadAssemblies(typeof(<DomainType>).Assembly, typeof(<InfrastructureType>).Assembly)
        .Build();

    [Fact]
    [Trait("Category", "Architecture")]
    [Trait("Rule", "DEP-01")]
    public void DEP_01_Domain_does_not_depend_on_infrastructure() =>
        Types().That().ResideInNamespaceMatching(@"^<Product>\.Domain(\..+)?$")
            .Should().NotDependOnAny(Types().That().ResideInNamespaceMatching(@"^<Product>\.Infrastructure(\..+)?$"))
            .Check(Architecture);

    [Fact]
    [Trait("Category", "Architecture")]
    [Trait("Rule", "DEP-02")]
    public void DEP_02_Namespaces_are_free_of_cycles() =>
        Slices().Matching("<Product>.(*)").Should().BeFreeOfCycles().Check(Architecture);
}
```

### 4. Benchmark project

Benchmarks live in a single console project whose name ends in `.Benchmarks`; the scripts find it automatically. Create it, add it to the solution, and reference the production project that owns the critical paths:

```bash
dotnet new console -n <Product>.Benchmarks -o benchmarks/<Product>.Benchmarks
```

```bash
dotnet sln {{solution}} add benchmarks/<Product>.Benchmarks/<Product>.Benchmarks.csproj
```

```bash
dotnet add benchmarks/<Product>.Benchmarks/<Product>.Benchmarks.csproj package BenchmarkDotNet --version 0.15.8
```

```bash
dotnet add benchmarks/<Product>.Benchmarks/<Product>.Benchmarks.csproj reference <ProductionProject>/<ProductionProject>.csproj
```

Replace `Program.cs` so the scripts can pass filters and exporters to BenchmarkDotNet:

```csharp
using BenchmarkDotNet.Running;

BenchmarkSwitcher.FromAssembly(typeof(Program).Assembly).Run(args);
```

Each benchmark class targets one critical path and is tagged with its ID from the guideline:

```csharp
using BenchmarkDotNet.Attributes;

[MemoryDiagnoser]
[BenchmarkCategory("CP-01")]
public class PlaceOrderBenchmarks
{
    private PlaceOrderHandler _handler = null!;
    private PlaceOrder _command = null!;

    [GlobalSetup]
    public void Setup()
    {
        // Build the real handler with in-memory dependencies and realistic data volume.
    }

    [Benchmark]
    public Task PlaceOrder() => _handler.Handle(_command, CancellationToken.None);
}
```

### 5. Restore

After cloning the repository or changing dependencies:

```bash
dotnet restore {{solution}}
```

```bash
dotnet tool restore
```

The scripts already run the restores they need and require no global .NET tools.

## Usage

Run from the repository root. If the root has more than one solution, every script accepts `-SolutionPath <path>` (PowerShell) or `--solution <path>` (Bash).

Coverage, complexity, CRAP score, and module size:

```bash
pwsh -NoProfile -File my-specs/measurement/run-coverage-report.ps1
```

```bash
bash my-specs/measurement/run-coverage-report.sh
```

By default the report opens in the browser. To only generate it, pass `-NoOpen` (PowerShell) or `--no-open` (Bash).

Coupling, which rebuilds the solution in `Release` with rule CA1506:

```bash
pwsh -NoProfile -File my-specs/measurement/run-coupling.ps1
```

```bash
bash my-specs/measurement/run-coupling.sh
```

Dependency conformance:

```bash
pwsh -NoProfile -File my-specs/measurement/run-architecture-tests.ps1
```

```bash
bash my-specs/measurement/run-architecture-tests.sh
```

To run only some rules, pass `-Rules DEP-01,DEP-02` (PowerShell) or `--rule DEP-01 --rule DEP-02` (Bash). The script exits with an error when a rule is violated, after writing the results.

Mutation score, which takes from minutes to hours on the whole solution:

```bash
pwsh -NoProfile -File my-specs/measurement/run-mutation.ps1
```

```bash
bash my-specs/measurement/run-mutation.sh
```

To mutate only a change's files, pass their repository-relative paths with `-Files src/A.cs,src/B.cs` (PowerShell) or `--file src/A.cs --file src/B.cs` (Bash), or mutate what changed since a commit with `-Since <ref>` or `--since <ref>`.

Benchmarks, which take minutes; close other heavy applications and keep the machine plugged in:

```bash
pwsh -NoProfile -File my-specs/measurement/run-benchmarks.ps1
```

```bash
bash my-specs/measurement/run-benchmarks.sh
```

To run only some critical paths, pass `-Categories CP-01,CP-02` (PowerShell) or `--category CP-01 --category CP-02` (Bash). Use `-Filter <glob>` or `--filter <glob>` to match benchmark names, and `-ProjectPath <path>` or `--project <path>` when the repository has more than one `*.Benchmarks.csproj`.

## Results

Every script deletes and recreates its own results folder on every run. `coverage/` and `benchmarks/` are ignored through `my-specs/measurement/.gitignore`; `coupling/`, `architecture/`, and `mutation/` carry their own `.gitignore`.

| File | Content |
| --- | --- |
| `my-specs/measurement/coverage/report/index.html` | HTML report with coverage, complexity, and *Risk Hotspots* (CRAP score) |
| `my-specs/measurement/coverage/report/Cobertura.xml` | Merged line and branch coverage, plus per-method `complexity` and executable lines |
| `my-specs/measurement/coverage/report/Summary.json` | Machine-readable summary, with `coverablelines` per class |
| `my-specs/measurement/coverage/raw/**/coverage.cobertura.xml` | Raw result for each test project |
| `my-specs/measurement/coupling/*.sarif` | SARIF log for each production project, with the `CA1506` results above the threshold |
| `my-specs/measurement/architecture/architecture_*.trx` | Architecture test results, one TRX per test project |
| `my-specs/measurement/mutation/reports/mutation-report.json` | Mutants per file, with status, mutator, and location |
| `my-specs/measurement/mutation/reports/mutation-report.html` | Browsable mutation report |
| `my-specs/measurement/benchmarks/results/*-report-github.md` | Benchmark table with `Mean` and `Allocated` per operation |
| `my-specs/measurement/benchmarks/results/*.json` | Machine-readable benchmark statistics and memory |

The CRAP score combines complexity and line coverage: `CRAP(m) = CC(m)² × (1 − cov(m))³ + CC(m)`. By default, ReportGenerator highlights complexity above 15 and CRAP above 30.

## What the scripts run

`run-coverage-report`:

1. Restores the solution packages and the local .NET tools.
2. Builds the solution in `Release`.
3. Runs the tests with the `XPlat Code Coverage` collector using `my-specs/measurement/coverlet.runsettings`, producing Cobertura files in `my-specs/measurement/coverage/raw/`. Tests in `*.ArchitectureTests.*` namespaces are left out: they only read the assemblies, add no coverage, and are measured by `run-architecture-tests`, so a violated rule does not stop this run.
4. Uses ReportGenerator to create the HTML report, the JSON summary, and the merged Cobertura file in `my-specs/measurement/coverage/report/`.

`run-coupling` rebuilds the solution in `Release`, without incremental build, importing `coupling.targets` into every project that is neither a test nor a benchmark project. That file enables rule CA1506 with the thresholds in `CodeMetricsConfig.txt` and writes one SARIF log per project to `my-specs/measurement/coupling/`; regular builds are unaffected.

`run-architecture-tests` runs `dotnet test` in `Release`, filtering the `Architecture` category, and writes the TRX results to `my-specs/measurement/architecture/`.

`run-mutation` runs Stryker.NET in solution mode with `my-specs/measurement/stryker-config.json` and writes the JSON and HTML reports to `my-specs/measurement/mutation/reports/`.

`run-benchmarks` finds the `*.Benchmarks` project, runs it in `Release` with the memory diagnoser, and exports JSON results, besides its default GitHub Markdown, CSV, and HTML reports, to `my-specs/measurement/benchmarks/results/`.

## Adapting to this repository

- In `coverlet.runsettings`, adjust `Exclude` to your test assembly names (the default excludes `*.Tests` and `*.xUnit.*`) and, to narrow the scope, add `<Include>[MyProduct.*]*</Include>`. Keep the same file exclusions in `mutate` of `stryker-config.json`.
- Keep the results folders out of version control and keep the scripts and configuration files versioned.
- If the benchmark project does not end in `.Benchmarks`, adjust the `[*.Benchmarks]*` coverage exclusion and the condition in `coupling.targets`, and pass the project path to `run-benchmarks`.
- To change the coupling thresholds, change `CodeMetricsConfig.txt` and the gates of `my-specs/metrics/coupling.md` together.
- Reflect every version, command, scope, or exclusion change in the affected metric files under `my-specs/metrics/`.

## Myspec integration

1. Install the dependencies above and run each script once to confirm its results are generated.
2. Run the `myspec-setup` skill to review and approve, all created with `Status: Proposed`:
   - one metric file per measurement under `my-specs/metrics/` (`cyclomatic-complexity.md`, `test-coverage.md`, `crap-score.md`, `module-size.md`, `coupling.md`, `dependency-conformance.md`, `mutation-score.md`, and `performance.md`), each with its own gates;
   - the `my-specs/general-guidelines/build-and-test-commands.md`, `my-specs/general-guidelines/dependency-rules.md`, and `my-specs/general-guidelines/performance-critical-paths.md` guidelines. Fill in the dependency rules, the critical paths, and their budgets before approving those guidelines.
3. Once approved, the `myspec-inspect` skill uses these commands to measure each spec's code, and the `myspec-quantify` skill uses them to produce the project-wide `my-specs/quality-report.md`.
