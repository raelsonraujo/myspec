# .NET quality: coverage, complexity, and CRAP score

This folder was generated by `myspec install --tooling dotnet-quality`. A single test run produces a report with:

- **line and branch coverage**, collected by `coverlet.collector`;
- **cyclomatic complexity** per method, class, and assembly, recorded by Coverlet in the Cobertura XML;
- **CRAP score** per method, computed by ReportGenerator in its *Risk Hotspots* section.

The `myspec` CLI **does not install dependencies**. Follow the steps below before the first run.

## Prerequisites

- A .NET SDK compatible with the project's solution;
- PowerShell 7+ to use `run-coverage-report.ps1`, or Bash for `run-coverage-report.sh` (on Windows, Git Bash or WSL);
- access to the NuGet feeds on the first run, to restore packages and local tools;
- Docker running only if the tests use Testcontainers or other container-based infrastructure;
- a single `.sln` or `.slnx` solution at the repository root, or a solution passed explicitly to the script.

## Installing the dependencies

### 1. Test packages

Add the packages to **every test project** the solution runs, replacing the example path with your test project's `.csproj`:

```bash
dotnet add <TestProject>/<TestProject>.csproj package Microsoft.NET.Test.Sdk --version 17.14.1
```

```bash
dotnet add <TestProject>/<TestProject>.csproj package coverlet.collector --version 6.0.4
```

These are the versions recorded in `my-specs/tooling.md`. If the project already uses other versions, confirm compatibility with the SDK and test framework and update `my-specs/tooling.md` before approving it.

### 2. ReportGenerator as a local tool

ReportGenerator is a **repository-local** tool, so every developer and CI use the same version. If the repository has no tool manifest yet, create one at the root:

```bash
dotnet new tool-manifest
```

Install the tool into the manifest (`dotnet-tools.json` at the root with the .NET 10+ SDK, `.config/dotnet-tools.json` with earlier SDKs):

```bash
dotnet tool install dotnet-reportgenerator-globaltool --version 5.5.10
```

### 3. Restore

After cloning the repository or changing dependencies:

```bash
dotnet restore {{solution}}
```

```bash
dotnet tool restore
```

The scripts already run both restores before generating the report and require no global .NET tools.

## Usage

Run from the repository root:

```bash
pwsh -NoProfile -File quality/run-coverage-report.ps1
```

```bash
bash quality/run-coverage-report.sh
```

By default the report opens in the browser. To only generate it, pass `-NoOpen` (PowerShell) or `--no-open` (Bash). If the root has more than one solution, pass `-SolutionPath <path>` or `--solution <path>`.

## Results

`quality/coverage/` is deleted and recreated on every run and is ignored by Git through `quality/.gitignore`.

| File | Content |
| --- | --- |
| `quality/coverage/report/index.html` | HTML report with coverage, complexity, and *Risk Hotspots* (CRAP score) |
| `quality/coverage/report/Cobertura.xml` | Merged line and branch coverage plus per-method `complexity` |
| `quality/coverage/report/Summary.json` | Machine-readable coverage summary |
| `quality/coverage/raw/**/coverage.cobertura.xml` | Raw result for each test project |

The CRAP score combines complexity and line coverage: `CRAP(m) = CC(m)² × (1 − cov(m))³ + CC(m)`. By default, ReportGenerator highlights complexity above 15 and CRAP above 30.

## What the scripts run

1. Restore the solution packages and the local .NET tools.
2. Build the solution in `Release`.
3. Run the tests with the `XPlat Code Coverage` collector using `quality/coverlet.runsettings`, producing Cobertura files in `quality/coverage/raw/`.
4. Use ReportGenerator to create the HTML report, the JSON summary, and the merged Cobertura file in `quality/coverage/report/`.

## Adapting to this repository

- In `coverlet.runsettings`, adjust `Exclude` to your test assembly names (the default excludes `*.Tests` and `*.xUnit.*`) and, to narrow the scope, add `<Include>[MyProduct.*]*</Include>`.
- Keep `quality/coverage/` out of version control and keep the scripts and `.runsettings` versioned.
- Reflect every version, command, scope, or exclusion change in `my-specs/tooling.md`.

## Myspec integration

1. Install the dependencies above and run the workflow once to confirm the report is generated.
2. Run the `myspec-setup` skill to review and approve `my-specs/tooling.md` and the `my-specs/general-guidelines/method-complexity-risk-targets.md` guideline, both created with `Status: Proposed`.
3. Once approved, the `myspec-quantify` skill uses these commands and results to produce each spec's `quality-report.md`.
