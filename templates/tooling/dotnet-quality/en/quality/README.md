# .NET quality: coverage, complexity, CRAP score, and performance

This folder was generated by `myspec install --tooling dotnet-quality`. A single test run produces a report with:

- **line and branch coverage**, collected by `coverlet.collector`;
- **cyclomatic complexity** per method, class, and assembly, recorded by Coverlet in the Cobertura XML;
- **CRAP score** per method, computed by ReportGenerator in its *Risk Hotspots* section.

A separate benchmark run measures **allocated bytes and mean time per operation** for the critical paths approved in `my-specs/general-guidelines/performance-critical-paths.md`, using BenchmarkDotNet.

The `myspec` CLI **does not install dependencies**. Follow the steps below before the first run.

## Prerequisites

- A .NET SDK compatible with the project's solution;
- PowerShell 7+ to use `run-coverage-report.ps1`, or Bash for `run-coverage-report.sh` (on Windows, Git Bash or WSL);
- access to the NuGet feeds on the first run, to restore packages and local tools;
- Docker running only if the tests use Testcontainers or other container-based infrastructure;
- a single `.sln` or `.slnx` solution at the repository root, or a solution passed explicitly to the script.

## Installing the dependencies

### 1. Test packages

Add the packages to **every test project** the solution runs, replacing the example path with your test project's `.csproj`:

```bash
dotnet add <TestProject>/<TestProject>.csproj package Microsoft.NET.Test.Sdk --version 17.14.1
```

```bash
dotnet add <TestProject>/<TestProject>.csproj package coverlet.collector --version 6.0.4
```

These are the versions recorded in the metric files under `my-specs/tooling/`. If the project already uses other versions, confirm compatibility with the SDK and test framework and update those files before approving them.

### 2. ReportGenerator as a local tool

ReportGenerator is a **repository-local** tool, so every developer and CI use the same version. If the repository has no tool manifest yet, create one at the root:

```bash
dotnet new tool-manifest
```

Install the tool into the manifest (`dotnet-tools.json` at the root with the .NET 10+ SDK, `.config/dotnet-tools.json` with earlier SDKs):

```bash
dotnet tool install dotnet-reportgenerator-globaltool --version 5.5.10
```

### 3. Benchmark project

Benchmarks live in a single console project whose name ends in `.Benchmarks`; the scripts find it automatically. Create it, add it to the solution, and reference the production project that owns the critical paths:

```bash
dotnet new console -n <Product>.Benchmarks -o benchmarks/<Product>.Benchmarks
```

```bash
dotnet sln {{solution}} add benchmarks/<Product>.Benchmarks/<Product>.Benchmarks.csproj
```

```bash
dotnet add benchmarks/<Product>.Benchmarks/<Product>.Benchmarks.csproj package BenchmarkDotNet --version 0.15.8
```

```bash
dotnet add benchmarks/<Product>.Benchmarks/<Product>.Benchmarks.csproj reference <ProductionProject>/<ProductionProject>.csproj
```

Replace `Program.cs` so the scripts can pass filters and exporters to BenchmarkDotNet:

```csharp
using BenchmarkDotNet.Running;

BenchmarkSwitcher.FromAssembly(typeof(Program).Assembly).Run(args);
```

Each benchmark class targets one critical path and is tagged with its ID from the guideline:

```csharp
using BenchmarkDotNet.Attributes;

[MemoryDiagnoser]
[BenchmarkCategory("CP-01")]
public class PlaceOrderBenchmarks
{
    private PlaceOrderHandler _handler = null!;
    private PlaceOrder _command = null!;

    [GlobalSetup]
    public void Setup()
    {
        // Build the real handler with in-memory dependencies and realistic data volume.
    }

    [Benchmark]
    public Task PlaceOrder() => _handler.Handle(_command, CancellationToken.None);
}
```

### 4. Restore

After cloning the repository or changing dependencies:

```bash
dotnet restore {{solution}}
```

```bash
dotnet tool restore
```

The scripts already run both restores before generating the report and require no global .NET tools.

## Usage

Run from the repository root:

```bash
pwsh -NoProfile -File quality/run-coverage-report.ps1
```

```bash
bash quality/run-coverage-report.sh
```

By default the report opens in the browser. To only generate it, pass `-NoOpen` (PowerShell) or `--no-open` (Bash). If the root has more than one solution, pass `-SolutionPath <path>` or `--solution <path>`.

Run the benchmarks separately; they take minutes, so close other heavy applications and keep the machine plugged in:

```bash
pwsh -NoProfile -File quality/run-benchmarks.ps1
```

```bash
bash quality/run-benchmarks.sh
```

To run only some critical paths, pass `-Categories CP-01,CP-02` (PowerShell) or `--category CP-01 --category CP-02` (Bash). Use `-Filter <glob>` or `--filter <glob>` to match benchmark names, and `-ProjectPath <path>` or `--project <path>` when the repository has more than one `*.Benchmarks.csproj`.

## Results

`quality/coverage/` and `quality/benchmarks/` are deleted and recreated by their scripts on every run and are ignored by Git through `quality/.gitignore`.

| File | Content |
| --- | --- |
| `quality/coverage/report/index.html` | HTML report with coverage, complexity, and *Risk Hotspots* (CRAP score) |
| `quality/coverage/report/Cobertura.xml` | Merged line and branch coverage plus per-method `complexity` |
| `quality/coverage/report/Summary.json` | Machine-readable coverage summary |
| `quality/coverage/raw/**/coverage.cobertura.xml` | Raw result for each test project |
| `quality/benchmarks/results/*-report-github.md` | Benchmark table with `Mean` and `Allocated` per operation |
| `quality/benchmarks/results/*.json` | Machine-readable benchmark statistics and memory |

The CRAP score combines complexity and line coverage: `CRAP(m) = CC(m)² × (1 − cov(m))³ + CC(m)`. By default, ReportGenerator highlights complexity above 15 and CRAP above 30.

## What the scripts run

1. Restore the solution packages and the local .NET tools.
2. Build the solution in `Release`.
3. Run the tests with the `XPlat Code Coverage` collector using `quality/coverlet.runsettings`, producing Cobertura files in `quality/coverage/raw/`.
4. Use ReportGenerator to create the HTML report, the JSON summary, and the merged Cobertura file in `quality/coverage/report/`.

`run-benchmarks` finds the `*.Benchmarks` project, runs it in `Release` with the memory diagnoser, and exports JSON results, besides its default GitHub Markdown, CSV, and HTML reports, to `quality/benchmarks/results/`.

## Adapting to this repository

- In `coverlet.runsettings`, adjust `Exclude` to your test assembly names (the default excludes `*.Tests` and `*.xUnit.*`) and, to narrow the scope, add `<Include>[MyProduct.*]*</Include>`.
- Keep `quality/coverage/` and `quality/benchmarks/` out of version control and keep the scripts and `.runsettings` versioned.
- If the benchmark project does not end in `.Benchmarks`, adjust the `[*.Benchmarks]*` coverage exclusion and pass the project path to `run-benchmarks`.
- Reflect every version, command, scope, or exclusion change in the affected metric files under `my-specs/tooling/`.

## Myspec integration

1. Install the dependencies above and run the workflow once to confirm the report is generated.
2. Run the `myspec-setup` skill to review and approve, all created with `Status: Proposed`:
   - one metric file per measurement under `my-specs/tooling/` (`cyclomatic-complexity.md`, `test-coverage.md`, `crap-score.md`, and `performance.md`), each with its own gates;
   - the `my-specs/general-guidelines/build-and-test-commands.md` and `my-specs/general-guidelines/performance-critical-paths.md` guidelines. Fill in the critical paths and their budgets before approving the performance guideline.
3. Once approved, the `myspec-inspect` skill uses these commands to measure each spec's code, and the `myspec-quantify` skill uses them to produce the project-wide `my-specs/quality-report.md`.
